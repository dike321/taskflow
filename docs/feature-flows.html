Akses · 01

Login & Sesi

Tidak ada backend/credential store nyata — login cuma mencocokkan email ke data user, password tidak diverifikasi. Logout menghapus seluruh data in-memory (bukan cuma sesi).

flowchart TD
    A([User buka /login]) --> B[Isi Email + Password]
    B --> C{Email cocok data user?}
    C -- Tidak --> D[Error: Email tidak terdaftar]
    D --> B
    C -- Ya --> E{Status user aktif?}
    E -- Tidak --> F[Error: Akun ini nonaktif]
    F --> B
    E -- Ya --> G[currentUser di-set, isAuthenticated = true]
    G --> H([Redirect ke /dashboard])
    H --> I{Klik Logout?}
    I -- Ya --> J[isAuthenticated = false]
    J --> K[Semua data Provider ter-unmount & reset]
    K --> L([Redirect ke /login])
    I -- Tidak --> M{Akses URL terproteksi tanpa login?}
    M -- Ya --> L
Catatan: pakai fitur switch user di header, bukan logout, kalau perlu ganti user tanpa kehilangan data transaksi yang sedang berjalan.

flowchart TD
    A([Admin buka Users]) --> B{Aksi?}
    B -- Add User --> C[Isi form: nama, email, role, company, warehouse]
    C --> D[Submit]
    D --> E[setUsers -> mutasi data user secara in-place]
    E --> F([User baru bisa langsung login])
    B -- Edit User --> G[Ubah role / warehouse / status]
    G --> H[Submit -> data user ter-update]
    H --> I([Perubahan berlaku saat user itu login berikutnya])

    J -- Ya --> K[Blokir: masih direferensikan sbg PIC/approver/reporter]
    J -- Tidak --> L[Konfirmasi hapus]
    L --> M([User terhapus])

Transaksi · 01

Stock In

Barang masuk gudang. Warehouse ter-lock otomatis kalau user punya warehouseId.

flowchart TD
    A([Buka Stock In]) --> B[Pilih Warehouse - locked sesuai user]
    B --> C[Pilih Item, Qty, Unit]
    C --> D{Qty > 0 & Warehouse terisi?}
    D -- Tidak --> E[Error validasi]
    D -- Ya --> F{Item batch-tracked?}
    F -- Ya --> G{Batch Number + Expiry diisi & belum dipakai item+warehouse ini?}
    G -- Tidak/Duplikat --> H[Error validasi batch]
    F -- Tidak --> I[Hitung base quantity]
    G -- Ya --> I
    I --> J{Qty ≤ Approval Threshold & user bisa approve?}
    J -- Ya --> K([Approved - stok & batch langsung dibuat])
    J -- Tidak --> L[Status: Pending]
    L --> M{Qty > Escalation Threshold?}
    M -- Ya --> N([Masuk antrian Approval 2 level])
    M -- Tidak --> O([Masuk antrian Approval 1 level])
Transaksi · 02

Stock Out

Barang keluar gudang, dipakai departemen tertentu. Tidak boleh melebihi stok tersedia.

flowchart TD
    A([Buka Stock Out]) --> B[Pilih Warehouse - locked sesuai user]
    B --> C[Pilih Item, Qty, Department]
    C --> D{Qty > 0?}
    D -- Tidak --> E[Error]
    D -- Ya --> F{Qty ≤ stok tersedia di warehouse ini?}
    F -- Tidak --> G[Error: Quantity exceeds available stock]
    F -- Ya --> H{Qty ≤ Approval Threshold & user bisa approve?}
    H -- Ya --> I([Approved - stok berkurang, FEFO consume batch])
    H -- Tidak --> J([Pending - alur Approval Berjenjang])

Stock Opname

Rekonsiliasi hasil hitung fisik vs catatan sistem.

flowchart TD
    A([Buka Stock Opname]) --> B[Pilih Warehouse + Item]
    B --> C[Sistem tampilkan System Stock]

Transaksi · 05

Batch & FEFO

diperbaiki 2026-09-22

Nomor batch sekarang divalidasi unik per item+gudang. FEFO tetap mengonsumsi batch expired (kebijakan produk, belum diubah).

flowchart TD
    A([Stock In item batch-tracked disetujui]) --> B[Batch baru dibuat: nomor, expiry, qty]
    B --> C([Muncul di halaman Batches])
    C --> D{expiryDate sudah lewat?}
    D -- Ya --> E[Badge: Expired]
    D -- Tidak --> F{Dalam 30 hari ke depan?}
    F -- Ya --> G[Badge: Expiring Soon]
    F -- Tidak --> H[Badge: OK]
    I([Stock Out item batch-tracked disetujui]) --> J[consumeFefo: ambil dari expiry paling awal dulu]
    J --> K[Termasuk batch Expired - tidak diblokir]
    K --> L[Kurangi qty batch itu, lanjut ke batch berikutnya kalau kurang]
Transaksi · 06

Approval Berjenjang

alur intidiperbaiki 2026-09-22

Dipakai bersama oleh Stock In/Out/Transfer/Opname. Self-approval sekarang diblokir — pembuat transaksi tidak bisa approve punya sendiri.

flowchart TD
    A([Transaksi status: Pending]) --> B{requiresSecondApproval?}
    B -- Tidak --> C{User = pembuat transaksi?}
    C -- Ya --> D([Tombol Approve/Reject disembunyikan])
    C -- Tidak --> E{canApproveAtLevel 1?}
    E -- Tidak --> D
    E -- Ya --> F{Approve atau Reject?}
    F -- Approve --> G([Status: Approved - stok/opname diterapkan])
    F -- Reject --> H([Status: Rejected])
    B -- Ya --> I{User = pembuat transaksi?}
    I -- Ya --> D
    I -- Tidak --> J{canApproveAtLevel 1?}
    J -- Ya --> K[Approve Level 1]
    K --> L([Status: Pending Final, catat approver level 1])
    L --> M{User baru = pembuat ATAU = approver level 1?}
    M -- Ya --> D
    M -- Tidak --> N{canApproveAtLevel 2?}
    N -- Ya --> O{Approve atau Reject?}
    O -- Approve --> G
    O -- Reject --> H
Satu-satunya guard maker-checker sebelum perbaikan: approver level 1 tidak boleh sama dengan approver level 2 di transaksi yang sama. Sekarang ditambah: pembuat transaksi tidak boleh approve transaksinya sendiri di kedua level.

Settings, Reports & Activity Log

Threshold approval dikonfigurasi di sini; tiap aksi tercatat ke Activity Log.

flowchart TD
    A([Admin buka Settings > General]) --> B[Ubah Approval Threshold]
    B --> C[Ubah Escalation Threshold]
    C --> D{Escalation ≤ Approval?}
    D -- Ya --> E[Error: harus lebih besar dari Approval Threshold]
    D -- Tidak --> F([Tersimpan, dipakai transaksi baru berikutnya])
    G([Setiap Create/Update/Delete/Approve/Reject]) --> H[logActivity: actor, module, deskripsi, timestamp]
    H --> I([Tampil di Activity Log - append only])
    F -.-> J([Reports: agregasi by category / warehouse / department])
    J --> K([Ter-scope ke warehouse user kalau warehouseId di-set])
